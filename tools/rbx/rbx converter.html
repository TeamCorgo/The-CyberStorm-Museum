How this was reverse-engineered
Decompiled from cstorm.exe in Ghidra: OpenResourceFile_FromArchive_2 binary-searches a sorted table of 16-byte directory entries (12-byte uppercase name + 4-byte offset) using RTL_MemCmp on the name field.
The offset field points to a location in the file holding a 4-byte length, immediately followed by that many bytes of data — that's the exact seek/read pattern the game performs before handing the buffer to FileHandle_SetVirtualWindow.
The one thing the disassembly didn't pin down directly is where the entry count and table itself start — that setup happens lazily elsewhere. This tool assumes the common layout, [u32 count][count × 16-byte entries] at offset 0, and falls back to scanning nearby offsets if that doesn't parse cleanly. If your file loads with 0 entries, it's a header layout this heuristic didn't catch.
